- zenith-float-num: a valid precision near the top of the range is no longer `InvalidArgument`. Root cause: the public precision check (`p_assertion`, `p <= MAX_PRECISION`) was also used inside the kernels on the precision they work at, which is the caller's precision rounded up to whole words (`round_p(MAX_PRECISION) = 2^60 > MAX_PRECISION`) or one word wider for a single correct rounding (`exact_bits` and `round_exact`: `round_p(p) + 64`), so `add`/`sub`/`mul`/`div`/`sqr`/the `_ref` forms/`div_exact`/`log` and the `round_exact` functions (`sqrt`, `hypot`, `fma`, `powi`, ...) refused every precision in `(MAX_PRECISION - 128, MAX_PRECISION]` except word multiples. Now the caller's precision is checked once, before any rounding, at the public entry (`prec_assertion`: in `exact_bits`, `round_exact`, `ExactNum::new`, the constructors, `set_precision`, `try_set_precision`, `ldexp`, `copysign`, `next_after`, `div_exact`, `convert_from_radix`), and inside the kernels `p_assertion` checks a working width against the exponent arithmetic only (twice the width fits the room `i64` leaves above `EXPONENT_MAX`, i.e. at most `2^61`; above that `MemoryAllocation`), derived from the arithmetic and not from `MAX_PRECISION`'s value. The wide-width sums use checked arithmetic. `parse`/`convert_from_radix` keep `usize::MAX` as "the precision of the numeral". Ball::powi/hypot/mul in zenith-float-bound inherit the fix (their top-of-range tests are no longer ignored). Still open, recorded and pinned only outside the range: the constant-building functions (`exp`, `ln`, `sin`, `atan`, `pow`, ...) spend hours building e/ln 2/pi toward 2^60 bits before an allocation fails (also true before this change at any valid precision near the top), and `fused_sum`/`fused_dot`/`polyval` call the public API at a working width, so they still report `InvalidArgument` at the top.
